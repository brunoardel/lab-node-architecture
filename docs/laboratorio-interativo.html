Modelagem de Domínio & Tipagem Estrita

Veja na prática a diferença entre o comportamento frágil do JavaScript puro e as defesas arquiteturais do TypeScript no projeto lab-node-architecture.

❌ No JavaScript / TS Ingênuo
FALHA SILENCIOSA

O desenvolvedor adiciona a regra "rural" no sistema, mas esquece de incluir no switch do motor de cálculo. O JS não reclama, pula silenciosamente e retorna undefined. 

function calcular(regra, area) {
  switch (regra.tipo) {
    case 'residencial': return area * 2.5;
    case 'comercial':   return area * 3.0;
    case 'industrial':  return area * 1.5;
    // Esqueceu 'rural' e não tem assertNever!
  }
}
// Entrada: { tipo: 'rural' }
// Retorno: undefined!
// Ao tentar ler retorno.area -> CRASH 500!

✅ No TypeScript com assertNever
BLINDAGEM EM COMPILAÇÃO

O bloco default recebe o tipo never. Se uma nova regra existir e não for tratada no switch, o TypeScript se recusa a compilar o projeto! 

function assertNever(x: never): never {
  throw new Error("Caso não tratado: " + x);
}

switch (regra.tipo) {
  case 'residencial': return area * 2.5;
  case 'comercial':   return area * 3.0;
  case 'industrial':  return area * 1.5;
  default:
    // Se faltou 'rural', regra NÃO é never!
    // TS2345: Argument of type 'RegraRural' 
    // is not assignable to parameter of type 'never'!
    return assertNever(regra);
}

💡 Por que isso importa na Arquitetura?

Em sistemas corporativos como a ArqLab, regras urbanísticas mudam frequentemente por decretos municipais. Sem assertNever, novos requisitos criam falhas fantasmas que só são descobertas quando o cliente final tenta calcular um projeto e a API quebra. Com assertNever, o compilador atua como auditor obrigatório: o código nem chega a ser publicado se alguém esquecer um caso!

❌ Tipagem Estrutural (Primitivos)
INVERSÃO DE IDENTIFICADORES

No TypeScript comum, type ProjetoId = string e type UsuarioId = string são 100% intercambiáveis (Duck Typing). Se você inverter a ordem dos parâmetros, o compilador aceita sem avisar. 

function deletar(projId: string, userId: string) {
  db.delete(projId, userId);
}

const userId = "user_999";
const projId = "proj_123";

// Parâmetros invertidos por engano:
deletar(userId, projId);
// TypeScript aceita silenciosamente!
// No banco: deleta o usuário achando que era projeto!

✅ Com Branded Types (Nominais)
ERRO EM TEMPO DE CÓDIGO

Adicionamos uma "marca" única (ex: & { readonly __brand: 'ProjetoId' }). Agora ProjetoId e UsuarioId são tipos incompatíveis, mesmo ambos sendo strings internamente! 

type ProjetoId = string & { readonly __brand: 'ProjetoId' };
type UsuarioId = string & { readonly __brand: 'UsuarioId' };

function deletar(pId: ProjetoId, uId: UsuarioId) { ... }

// Ao tentar inverter:
deletar(userId, projId);
// ❌ TS2345: Argument of type 'UsuarioId' is 
// not assignable to parameter of type 'ProjetoId'.

❌ Ilusão do TypeScript na Borda
TYPE ERASURE EM PRODUÇÃO

Em produção, o Node.js executa JavaScript puro. Todas as interfaces e types do TypeScript são apagados (type erasure). Se o cliente HTTP enviar campos inválidos ou strings onde deveriam ser números, o Node.js não sabe! 

// O desenvolvedor acha que a interface protege a rota:
app.post('/calcular', async (req) => {
  const dados = req.body as DadosProjetoUrbanistico;
  // Se o cliente enviar { areaTerreno: "mil" } ou negativo:
  return dados.areaTerreno * 2; // NaN ou erro!
});

✅ Defesa de Borda com Zod
VALIDAÇÃO ATIVA EM RUNTIME

O Zod atua na borda da API como a alfândega. Ele valida e sanitiza o payload JSON em tempo de execução, rejeitando dados anômalos com HTTP 400 antes de contaminar as funções de domínio. 

const schema = z.object({
  areaTerreno: z.number().positive(),
  regraZoneamento: z.discriminatedUnion('tipo', [...])
});

// Se o cliente enviar dados errados:
// 400 Bad Request: "areaTerreno deve ser maior que zero"
